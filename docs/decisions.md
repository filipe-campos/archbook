# Decisions

Choices made where the v0.1 brief left room, newest topics last. Each entry says what was decided and why.

## Packaging and tooling

- **Only `archbook` is published.** `@archbook/schema` and `@archbook/viewer` are `private`. The CLI bundles the schema code with tsup and copies the built viewer, the plugin and the JSON Schemas into its package (`viewer/`, `plugin/`, `schema/`). No npm organization is needed for v0.1.
- **The npm README is a build copy.** The CLI build copies the root `README.md` into `packages/cli/` and turns its relative links into GitHub URLs at the `v<version>` tag, because npm resolves relative links against `packages/cli/`. The root README keeps relative links, so it still works on GitHub and in forks.
- **Zod 4 with its native `z.toJSONSchema()`** instead of `zod-to-json-schema`, which does not support Zod 4. The JSON Schema targets draft-07 because editors support it best, and uses the input shape, so fields with defaults are optional.
- **TypeScript 6.0, not 7.** typescript-eslint supports TypeScript up to 6.0.
- **commander 14, not 15.** commander 15 needs Node 22; the CLI supports Node 20.12+ (the floor of `@clack/prompts`).
- **Node versions.** Using the CLI needs Node 20.12+. Developing Archbook needs Node 22.18+, because tsup 9 and Vite 8 require it. CI builds on Node 22 and 24, then packs the CLI, installs the tarball in an empty folder on Node 20.12 and runs it there, so a missing file in `files` or a dependency left in `devDependencies` fails CI.
- **`@types/node` follows the development floor (22).** Newer majors would type APIs that Node 20 and 22 lack, so Dependabot ignores them; move it only together with the Node versions above.
- **Live types inside the monorepo.** Package `exports` carry an `@archbook/source` condition that points at `src/`. TypeScript (`customConditions`) and esbuild resolve it, and Vite and Vitest use aliases, so typecheck, tests and `pnpm dev:example` work without building the schema first.
- **CSS modules plus one global theme file** (CSS variables for light and dark) rather than Tailwind.
- **pnpm 11 build approval.** `pnpm-workspace.yaml` allows esbuild's install script (`allowBuilds`); pnpm 11 blocks unapproved ones.
- **The live reload hub lives in `@archbook/schema/node`.** `archbook dev` and the Vite plugin behind `pnpm dev:example` share `createLiveReloadHub` (directory watch, one 80 ms debounce, SSE clients, keep-alive pings), and the viewer reads the event name from the same `protocol.ts`. It is the Node half of the contract between the servers and the viewer, and the schema is the only package all of them share. The main entry cannot import it, so the viewer bundle stays browser-safe.
- **Coverage limits are the coverage at the time they were set.** Each package's `vitest.config.ts` sets V8 coverage thresholds at the measured values, rounded down, and CI runs `pnpm test:coverage`. They only stop regressions; raise them when tests grow.
- **Component tests run in happy-dom, end-to-end tests in Chromium.** Viewer component tests opt in with `// @vitest-environment happy-dom` per file, so the pure tests keep the Node environment. The canvas depends on layout and `ResizeObserver`, so it is covered by Playwright in `e2e/`, against the site `archbook build` writes and against `archbook dev`. The e2e fails on any console error or Content Security Policy violation.
- **`yaml` reads the recipe frontmatter.** The CLI depends on the `yaml` package rather than a hand-written parser, so recipe authors can use any YAML they know (flow lists, quoted scoped names, comments).
- **Windows is checked but not required.** A Windows job builds and tests on every push with `continue-on-error`, until the open point below is settled.

## Schema

- **All ids are strict kebab-case** (`^[a-z0-9]+(?:-[a-z0-9]+)*$`) for nodes, edges, groups and flows. Flow ids appear in URLs, and one rule is easier to remember than four.
- **Objects are strict.** Unknown keys are schema errors, so typos such as `sumary` are caught instead of ignored.
- **`FlowStep.reverse`** (added). A step can travel an edge backwards, for HTTP responses and webhook acknowledgements, without a second edge per response.
- **Flow continuity** (`discontinuous-flow` warning). The brief's rule (the next step starts where the previous ended) flags every service that calls two dependencies in a row. The rule is: a non-async step must start at a node the flow has already reached, since a synchronous call returns to its caller.
- **Extra validation codes.** `group-cycle` (nested groups must not loop, or the viewer could not lay them out) and `invalid-source-path` (absolute paths, `..` escaping the project, backslashes).
- **Source references may point to directories.** Then `lines` is an error.
- **`project.description` defaults to `""`**, as in `config.json`. A real generation omitted the empty description, which an earlier strict version of the schema rejected.
- **`position` is relative to the parent group** when the node has one, matching how the canvas nests nodes. Groups grow to fit nodes moved by hand.
- **Validation has two entry points.** `@archbook/schema` is browser-safe and checks shape and references. `@archbook/schema/node` adds the disk checks (file exists, line range fits) through a `SourceFileIndex`. The viewer runs the first; the CLI runs both.
- **`$schema` URL** is `https://unpkg.com/archbook@0.1/schema/architecture.schema.json`, served from the published CLI package. The schema package builds the URLs from `SCHEMA_VERSION`, and tests check that the docs, the `schema` skill and the plugin commands use the same version.
- **`config.json` reuses the `project` shape of `architecture.json`**, so the two cannot drift apart.
- **`language` is a BCP 47 language tag** (`en`, `pt-BR`, `zh-Hant-TW`) in both `architecture.json` and `config.json`, checked by the same pattern `init` uses. Earlier documents accepted any string of two or more characters; a value such as `english` is now a schema error, which is acceptable before 1.0.
- **Validation codes are data.** `ISSUE_CODES` lists every code with its severity, so a code always has the same severity. Tests check that `docs/schema.md`, the `schema` skill and the validator agent list exactly these codes, with matching severities where they show one.
- **Validation runs as small rules over a shared index.** `indexArchitecture` builds the lookups once (items by id, edges in and out of each node, flow steps per edge, groups that hold nodes), and each rule in `src/rules/` reports through one `report` function. `RULES` fixes the order of the issues, which tools and tests rely on. When ids repeat, the index keeps the first item, so references resolve to the same item everywhere. The viewer can use the same index.
- **Warnings for what the viewer hides.** `self-loop-edge` and `empty-group` flag edges and groups the viewer does not draw, so nothing disappears silently. `duplicate-edge` checks the modelling rule "one edge per pair of nodes and kind"; it is a warning because flows sometimes need two interactions of the same kind told apart. An edge whose id already repeats an earlier one gets only the `duplicate-id` error.
- **Links and `repoUrl` accept only `http` and `https`.** The published site renders these values as links, and React 18 still renders `javascript:` hrefs, so any other scheme is a schema error in `architecture.json` and `config.json`. Hosts without a dot (`http://localhost:3000`, `http://grafana/`) stay valid, which is why the schema uses `z.url()` with a protocol check rather than `z.httpUrl()`. The viewer also drops non-http(s) hrefs, for documents that were never validated. This breaks documents that used other schemes, which is acceptable before 1.0.
- **`diffArchitecture` ignores key order and volatile fields** (`generatedAt`, `generatedBy`, `$schema`). It reports added, removed and changed ids per collection, plus the changed fields.

## Viewer

- **Layout.** ELK `layered`, left to right, with `INCLUDE_CHILDREN` for nested groups. Children are added in document order and cycles are broken by model order, so the first node (usually the actor) starts on the left. Groups with no nodes are not drawn. Layering is `LONGEST_PATH_SOURCE`, set on the root and on every group because ELK reads it per graph level: each node sits as early as its callers allow, so entrypoints come first and data stores and providers last, in reading order.
- **Edges follow ELK's routes.** Edges are drawn along the orthogonal routes ELK computes (`elk.json.edgeCoords: ROOT` returns them in canvas coordinates across groups), with rounded corners, and labels go where ELK reserved room for them. Earlier Bezier curves between handles ignored the layout and crossed components. An edge touching a node with a manual `position` has no valid route and falls back to a curve.
- **Replay camera.** A step is framed with a zoom ceiling of 0.9, so neighbors stay in view and the scale stays steady between steps, and the minimap is hidden while a flow plays so the stage holds only the story.
- **Replay timing.** Real durations (1 ms to minutes) are clamped to 0.6 to 2.4 s of travel, so slower steps still look slower but nothing flashes by. Each step stays on screen for its travel time plus 1.8 s of reading time, divided by the speed.
- **URLs.** `#/flow/<id>/step/<n>` (1-based), `#/flow/<id>`, `#/node/<id>` and `#/edge/<id>`. Playback uses `replaceState`, so the browser history does not fill with steps.
- **Inspecting during a replay.** Clicking a node while a flow is open shows its details without leaving the flow; the panel goes back to the step when the replay moves on.
- **Reloads keep the last valid document.** When a live reload finds the file invalid or missing after a valid version was shown, the viewer keeps that version and shows a banner with the first errors, so a half-saved edit does not replace the diagram with the error screen. The first load still shows the error screen. Only the newest reload request is applied.
- **Disk checks are not repeated in the browser.** The error screen shows shape and reference errors; `archbook validate` and the `dev` terminal output cover file paths.
- **Source links** follow GitHub, GitLab and Bitbucket URL shapes, based on the host of `project.repoUrl`.
- **Layout runs in a Web Worker.** ELK can take seconds on large graphs, so the viewer runs it in a worker built from `elkjs/lib/elk-worker.min.js`, copied as is and loaded by a URL relative to the bundle, which keeps sub-path hosting working. Where `Worker` is missing or the worker fails to load, the viewer falls back to ELK on the main thread; a graph ELK rejects is reported, not laid out again. The Markdown renderer loads on first use, which keeps the main bundle under 500 kB.
- **Keyboard and screen readers.** Components and unlabelled edges are tab stops, named by name and kind, and Enter or Space opens them like a click; a labelled edge is reached through its label, which is a button. Search follows the WAI-ARIA combobox pattern, and the replay announces each step. A key a focused element handles is not also a global shortcut, so Space on a component opens it instead of pausing.
- **Reduced motion.** With `prefers-reduced-motion`, the replay draws no travelling dot (the active edge stays highlighted) and the camera jumps instead of gliding.
- **Pure `graph/` and `lib/`.** Layout, highlight and the other viewer logic import no React, React DOM or icons (`@xyflow/react` only for types), so they run in plain unit tests. Contexts, icons and hooks live in `components/` and `hooks/`, and ESLint checks the boundary. The viewer looks items up through `indexArchitecture`, built once per document.
- **Content Security Policy.** The built site carries `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'` in a meta tag (`packages/viewer/csp.ts`), so a document that slips a script or an outside URL past validation still cannot run or load it. The exceptions: `'unsafe-inline'` styles, because React Flow positions nodes and the viewer sets colors through `style` attributes; `data:` images for the inline favicon. The layout worker and the live reload stream are same-origin, so `archbook dev`, which serves the same build, needs nothing more. Zod runs in `jitless` mode in the viewer, set before any schema is created, because its check for `eval` would otherwise be reported as a violation. The meta tag is added only by `vite build`, since Vite's dev server injects inline scripts. A meta tag cannot set `frame-ancestors`; hosts that need it must send the header.
- **Visual language.** Dark-first "tech premium" styling: translucent surfaces with backdrop blur, one accent gradient (violet to cyan) reserved for what is active or actionable, kind colors only on icons and the card's top line, and monospace for technical labels (kinds, chips, eyebrows, counters). All of it lives in the tokens of `styles/theme.css`, so both themes follow the same rules.
- **Bundled fonts.** Inter and JetBrains Mono come from `@fontsource-variable` and ship as same-origin files, because the Content Security Policy blocks font hosts and the site must work offline. Only the subsets a page uses are downloaded, and the fonts are not part of the main JavaScript bundle.
- **Replay is the first action.** When no flow is open, a button on the canvas replays the first flow, since replaying is what the viewer offers that a static diagram does not. The other flows stay in the overview panel.
- **README image.** `pnpm readme:image` builds the example with the CLI, captures a step of the Checkout replay in the dark theme and frames it in a browser window (`scripts/readme-image.mjs`), so the picture can be regenerated after any visual change.

## CLI

- **Layers.** The CLI source is split into `commands/` (read options, call the domain, print), `core/` (use cases and rules, no terminal), `io/` (side-effect adapters) and `ui/` (pure text formatting). The domain is testable without a terminal, user decisions reach it as callbacks such as `confirmOverwrite` and `confirmEdited`, and commands stay thin. ESLint checks the boundaries; see "CLI layers" in `CONTRIBUTING.md`.
- **Output port.** Commands print only through `context.output` (`Output` in `io/output.ts`), the counterpart of `Prompter`. Tests pass a memory output, so `pnpm test` stays quiet and can assert on messages. A terminal on stdout gets clack's live log for `generate`; otherwise its progress is plain lines for CI logs and files. The rest of the output is the same in both cases. The choice depends on stdout alone, unlike the `Prompter`, which needs stdin too, so `archbook generate < /dev/null` in a terminal keeps the live log.
- **Project root.** Commands walk up to the nearest folder with `archbook/config.json`, `architecture.json` or `.manifest.json`, so they work from sub-folders. `init` always uses the current folder.
- **Snapshots** are one JSON file each in `archbook/.history/<timestamp>-<operation>.json`, holding the exact text of `architecture.json` (or `null` when it did not exist) with its metadata, so restoring is byte for byte. A snapshot is skipped when the newest one already holds the same content.
- **`undo` restores the newest snapshot that differs from the current file** (restoring an identical one would look like a no-op), after snapshotting the current state as `undo`. Running it twice therefore redoes.
- **`snapshot` prints `Time: <ISO 8601>`, `Schema: <URL>` and `Generated-By: <value>`.** Headless sessions cannot run `date`, so the commands take `generatedAt` from the first line, and `$schema` and `generatedBy` from the others instead of writing them by hand.
- **The code merges, the model decides.** The Claude Code commands write each agent's output to `archbook/.drafts/<name>.json` and run the hidden `archbook merge --draft <file>`, which validates the result (with the disk checks), writes it formatted, deletes the draft and prints a JSON report (`added`, `removed`, `reused`, `renamed`, `replaced`, `preserved`, `validation`). Which elements are the same component and what to drop stay in the prompts, since they need judgment. The rules:
  - With `--replace-structure`, a scanner draft's groups, nodes and edges replace the document's, and kept node ids keep their previous `owner`, `links` and `position`. Flows stay; the flow drafts that follow replace them one by one.
  - A flow draft adds `newNodes` whose id is new, reuses an existing edge with the same `from`, `to` and `kind`, renames an edge whose id belongs to different endpoints to `<id>-2`, `<id>-3` and so on, points the steps at the result, and replaces the flow with the same id or appends it.
  - A scanner draft without `--replace-structure` (used by `/archbook:sync`) only adds new ids, with the same edge reuse.
  - A draft may also set the top-level fields (`$schema`, `version`, `project`, `audience`, `language`, `generatedAt`, `generatedBy`), so the first generation needs no file to start from.
  - Drafts must be inside `archbook/.drafts/`, because the command deletes them. When the merged document fails the schema, nothing is written, the draft stays and the exit code is 1. Semantic errors are written and reported, like the output of `generate`, so the validator agent can fix them. It takes no snapshot: the command that runs it already took one.
- **`archbook format` writes the canonical form.** Keys follow the schema's field order, which is the order `docs/schema.md` documents. Optional empty arrays, empty strings and `false` are left out, because the viewer reads them as absent; `payload` is copied as is. Only documents that pass the schema are formatted, semantic errors do not matter. It snapshots as `format` before rewriting `architecture.json`; `--file` rewrites another file without a snapshot, since snapshots hold `architecture.json` only. CI runs `format --check` on the example, so the example's `architecture.json` is left to `archbook format` instead of Prettier, whose array wrapping differs.
- **Versions move together.** Every package and the plugin manifest carry the CLI version; a test keeps them equal.
- **Uncommitted changes** to `architecture.json` produce a warning in `generate` and in `snapshot --op generate|sync`. Nothing is blocked, because the snapshot keeps them.
- **Errors.** Expected failures (bad config, unknown snapshot, invalid manifest) print one line without a stack trace. Anything else prints `Unexpected error: <message>` and a hint; the stack trace appears only with `ARCHBOOK_DEBUG=1`.
- **Options are checked by commander.** `dev --port` takes a whole number from 1 to 65535, and the hidden `snapshot --op` accepts only the operations that snapshot before writing (`generate`, `sync`, `add-flow`, `explain`, `format`); `undo` snapshots itself internally.
- **Snapshot files are validated.** History and `undo` skip files that do not match the snapshot format, and asking for such a snapshot by id is an error.
- **An unreadable previous document is not a new file.** Diffs treat a missing file as absent and a file that is not valid JSON as an empty document, so summaries never say "file created" about a file that existed.
- **`.gitignore`** gets `archbook/.history/`, `archbook/.drafts/` and `archbook/dist/` (the build output is an artifact too). Re-running `init` appends the lines an older install lacks, and `remove` deletes `.drafts/` with the other tool files.
- **Detection recipes declare their packages.** The npm packages that reveal a technology live in the `detect` frontmatter of its recipe, and `archbook init` reads them from the bundled plugin, so one file teaches both the agents and the CLI. File-based signals (Go, Python, Terraform, Docker and so on) stay in the code, since most have no recipe. Signals list file rules first, then package rules in recipe file name order, and each carries the `recipe` that covers it, so the scanner opens exactly those recipes. Invalid frontmatter is an unexpected error, not a user error: recipes ship with the CLI, and a test checks every one of them.
- **`init --yes`** answers every question with its default and does not start a generation unless `--generate` is passed, so automation never spends tokens by surprise.
- **Re-running `init`** updates assets that are unchanged since the last install, and asks before overwriting anything else. An overwritten user file is recorded with its original content, which `remove` restores.
- **Generation phases.** `generate` follows the orchestrating session's agent launches (`scanner`, `flow-tracer`, `writer`, `curator`, `validator`) and its `archbook snapshot`, `merge` and `validate` calls. Each phase gets its own live log, which shrinks to one line with its duration when the next phase starts. Only top-level calls move the phase, because agents also run `archbook validate` on their own. The phase list lives in `GENERATION_PHASES`, and the note shown before a run is built from it.
- **Generation summary.** A run ends with a card: component, connection, flow and group counts, then the changes, the time and the cost. The validation report is printed only when it has errors or warnings, since a clean result adds nothing to the card.

## Claude Code integration

- **Plugin names are the source of truth.** Files in `plugin/` use plugin names: `/archbook:generate`, the `archbook:scanner` agent, the `archbook:schema` skill. `init` copies them to `.claude/` with an `archbook-` prefix and rewrites the references, because project folders have no namespaces.
- **How `generate` starts Claude Code.** It runs `claude -p "/archbook-generate"` when `init` installed the command, otherwise `claude -p "/archbook:generate" --plugin-dir <bundled plugin>`, with `--output-format stream-json --verbose`.
- **Slash command fallback.** Claude Code passes an unknown slash command to the model as plain text, so `generate` checks `slash_commands` in the `system/init` message. When the command is missing it stops that session and sends the command's instructions as the prompt.
- **Permissions.** The session gets Read, Glob, Grep, Skill, `Edit(./archbook/architecture.json)` and `Edit(./archbook/.drafts/**)` (which also cover Write) and Bash only for `archbook validate`, `snapshot`, `merge` and `format` (with or without `npx`), read-only `git` subcommands, `ls` and `wc`. `merge` writes only `architecture.json` and deletes only drafts; `format` rewrites only files that already pass the schema, without changing what they say. The plugin commands' `allowed-tools` use the same Archbook rules, and a test keeps them in sync. Code being scanned can carry prompt injection, so the session cannot run `remove`, `undo` or `init`, or rewrite `config.json` and `.manifest.json`. Agents keep plain `Edit` and `Bash`, because their `tools` field cannot restrict subcommands. The Agent tool needs no permission.
- **`archbook` on PATH.** `npx` ignores binaries on PATH, so the session gets a temporary `archbook` shim that runs the same CLI build (its `sh` script single-quotes both paths), plus an appended system prompt. The prompt says to use `archbook` instead of `npx archbook` and that no user can answer questions.
- **Failure handling.** A non-zero exit, an error result, Ctrl+C or an unexpected error in the CLI restores the snapshot. Stream messages without the fields Archbook reads are ignored, and an error while handling one never stops the run. Output that is not valid JSON or fails the schema is also restored, and the broken file is kept in the temp folder. Output with only semantic errors (a wrong path, say) is kept and reported, so `/archbook-generate` or a quick fix can finish it.
- **Plugin removal.** `archbook remove` reads `claude plugin list --json` and prints the exact `claude plugin uninstall <id> --scope <scope>` command when an Archbook plugin is installed.
- **A curator pass polishes presentation.** `archbook:curator` runs after the writer and before the validator in `/archbook:generate`, `/archbook:sync` and `/archbook:add-flow`. It edits only display fields (node names and tech chips, edge labels, group and flow names, step titles, payload example values) to fit how the viewer renders them, and never ids, structure or facts. The writer owns whether text is true; the curator owns how the document reads as a whole. Keeping them as two agents means each prompt does one job.
- **The writing guide carries the viewer's limits.** The sizes in "Presentation in the viewer" (22-character node names, 3 visible tech chips, 24-character edge labels, 48-character step titles, payloads of about 12 lines) come from the viewer's card, pill and timeline sizes. Change them together with the viewer.

## Remove

- **Manifest entries**: `created` (with the content hash), `replaced` (with the original content), `modified` (the exact text appended, plus whether the file was created) and `created-dir`.
- **`archbook/` is deleted as a whole only when `init` created it.** Otherwise only Archbook's own files inside it are removed.
- **Edited files.** Interactively, `remove` asks about each file whose hash changed. With `--yes`, or without a terminal, it keeps them and lists them.
- **Without a manifest** (conservative mode), `remove` targets `archbook/` and the `archbook-*` entries in `.claude/commands|agents|skills`, and always requires an interactive confirmation, even with `--yes`.
- **The manifest is validated.** `archbook/.manifest.json` is committed and editable, so `remove` and `init` check its shape and require every path to be relative, canonical and inside the project. An invalid manifest stops the command with an error instead of falling back to conservative mode. Every path is also resolved against the project root before anything is deleted or written.
- **Backups** are written with node-tar to `$TMPDIR/archbook-removed-<timestamp>.tar.gz`, for portability.
- **Removing appended text** strips the exact bytes that were added, so a `.gitignore` without a trailing newline comes back identical. If the user edited the block, its lines are removed one by one, and lines added later stay.

## Open points

- **Windows.** The CLI is built and tested on Windows in CI, but the job may fail without blocking. `generate` spawns `claude` without a shell, which cannot start the `.cmd` shim npm installs on Windows, so starting Claude Code there may need `shell: true` or resolving `claude.exe`; for the same reason the `generate` tests, which run a fake `claude` written in JavaScript, are skipped on Windows. The `archbook` shim has a `.cmd` variant.
- **LF everywhere.** `.gitattributes` checks every text file out with LF, so Windows clones keep `architecture.json` in its canonical form and frontmatter parses the same as on Unix.
